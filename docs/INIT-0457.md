# Initialization layout in official 0.4.57c

Inspected the official distribution's `Endless.exe` locally for interoperability; no account information was involved. Source download: https://www.endless-online.com/client/0_04/EndlessOnline0457c.zip . Executable SHA-256: `da63424346a773ae6bdd75568179be8e615e67262ea2c0316985d321283accf0`.

The exported `TMainForm::clientConnect` at virtual address `0x41e014` calls the initialization builder at `0x4f32bc`. Its byte builder at `0x4f9fd4` encodes unsigned base-253 values with 254 padding and the requested output width.

Observed request body order:

| Field | Bytes | Evidence (virtual address) |
|---|---:|---|
| Init action/family | 2 raw 255 bytes | `0x4f33da`–`0x4f3483` |
| Randomized difference | 3 encoded | `0x4f348e`–`0x4f34b6` |
| Major/minor/patch | 1 encoded each | `0x4f3505`, `0x4f3576`, `0x4f35e7` |
| Protocol marker 113 | 1 encoded | `0x4f3658`–`0x4f366c` |
| Actual challenge | 3 encoded | `0x4f36bb`–`0x4f36d4` |
| Installation ID length | 1 encoded | `0x4f3723`–`0x4f3746` |
| Installation ID | length bytes | `0x4f3795`–`0x4f37b1` |

The builder selects the actual challenge using random modulo 1,000,000 at `0x4f33b1`. The first three-byte value is the unsigned difference between that value and another random modulo 1,000,000 (`0x4f3490`). Encoding the low three base-253 digits is equivalent to reducing the unsigned value modulo 253³. The frame prefix is the encoded body length, two bytes (`0x4f37cc`).

This differs from the older public Recharged XML, which places only one challenge before the version fields and no additional value after marker 113. Our classic request layout is unchanged. The corrected Recharged request is covered by offline checks for the prefix, actual challenge position, installation length, bounds and preservation of the classic layout.

This static comparison does not establish the current success-response layout, challenge-response algorithm, authentication or playable compatibility. Live validation results are recorded in COMPATIBILITY.md.

## Success response processing

At `0x4f46be` the client branches on reply code 2 and checks for at least 15 bytes. It decodes the two two-byte parameters at body offsets 5 and 7, the player ID at offset 9, and a three-byte value at offset 11. At `0x4f482e` that last value is stored at connection-object offset 0x30; the success branch proceeds without comparing it to the classic challenge hash. At `0x4f4841`–`0x4f4868`, a byte-sized parameter initialized as challenge modulo 250 is incremented by 2 and the final response byte. Sequence setup at `0x4f8e0c` also adds challenge modulo 11 to one parameter.

Our diagnostic therefore reports `init-received` for this exact well-formed layout, not classic-hash failure or a completed session. The official client subsequently sends Connection/Accept (`0x4f4984`–`0x4f4989`); the session check implements that encoded exchange.

## Connection acknowledgement and packet transform

The current send path at `0x4f8e7c` writes raw action/family, a one-byte encoded sequence and payload. The sequence counter increments before use and cycles 0–9; its base is the sum of initialization bytes 3 and 4 minus 11 (`0x4f46de`–`0x4f4745`). The effective outgoing parameter is the short at offset 7 plus challenge modulo 11 (`0x4f8e0c`); the incoming parameter is the short at offset 5.

`0x4f914c` transforms each body byte at zero-based index i to `(byte + parameter + i + 4) mod 256`. `0x4f91d0` reverses this. The two-byte encoded length prefix remains outside that transform. This is protocol obfuscation, not authenticated transport encryption.

The acknowledgement at `0x4f4888`–`0x4f4989` uses action 3 / family 1 and three encoded shorts: effective outgoing parameter, incoming parameter, player ID. The official encoder truncates to the requested base-253 width. `RechargedSession` implements this exchange and the CLI exposes an opt-in `--session-check`: send init, send one acknowledgement only after a valid init response, observe one packet for at most 20 seconds, and close. It never sends account credentials or game actions. A packet received after acknowledgement is reported with its decoded action/family and length; it is not automatically claimed to be authenticated gameplay or a fully verified keepalive session.

## Pre-login synchronization

The Login-family handler at `0x508fab` recognizes action 244 and calls `0x5052bc`. That routine sends action 244 / family 3 with the literal ASCII `k` from address `0x7beca7`. The observed server packet is three bytes after decoding. The session check recognizes this layout, sends the reply once, then disconnects. This verifies receipt and local transmission, not server acceptance of the reply or authentication. The iPhone connection check now uses this same bounded flow. Offline golden vectors cover acknowledgement, synchronization reply, sequence progression, and transformation wrapping.

## Keepalive and sustained observation

Connection/Ping (action 21 / family 1) is handled at `0x50848d`. The six-byte payload contains an encoded char divisor, encoded four-byte dividend, and an encoded trailing char. At `0x5085b1` the new sequence base is `(dividend - 12) / divisor - divisor`; `0x4f8e44` replaces the base without resetting the ten-step counter. The reply builder `0x505254` sends action 241 / family 1 with ASCII `k` (literal at `0x7beca5`). Invalid lengths, zero divisors and negative sequence results are rejected locally.

CLI `--session-watch` and the iPhone connection check observe for at most 45 seconds after acknowledgement and answer recognized synchronization and keepalive packets. Unknown packets stop the observation, and a 64-packet cap bounds unsolicited traffic. Neither mode retries or transmits credentials. This is a bounded diagnostic, not yet a persistent gameplay connection.

## Credential submission investigation

The user’s localhost dummy-login attempts produced action 35 / family 2 after acknowledgement and synchronization (payload lengths 50 and 45). The lab deliberately closed on that unhandled packet; this was not a server password rejection.

Builder `0x5050b8` encodes its first string with parameter 123, appends byte 255, encodes its second string with byte `(connection[0x38] + 130)`, then appends 255 and sends action 35 / family 2. Encoder `0x4f5e78` uses one-based positions: add parameter times position modulo 256, subtract 12 at even positions modulo 256. Every third position adds 60 and emits three base-24 digits; other positions emit two. Each digit is offset by ASCII A. The initial output literal at `0x7bcae4` is empty.

`RechargedCredentials.Encode` implements this transformation but is not wired to live account submission. The updated loopback lab compares only the known dummy pair testuser / TestOnly123 in memory, recording a match boolean and lengths. No credential payloads are logged. Real-client comparison passed: the official client sent action 35 / family 2 with a 45-byte payload matching the dummy pair exactly. The native bounded sign-in test now uses this encoder; server response interpretation and world entry remain incomplete.


User native sign-in test returned action 3 / family 2, 82 decoded bytes. Only metadata was retained, so its result code is unknown. Official handler 0x5967e1 selects family 2; 0x5970e4 selects action 3, reads the first payload short and enters the accepted branch only for code 1 (0x597158). The first FF-delimited segment has numeric fields at one-based positions 3/2, 5/2, 7/1, 8/2, 10/2, 12/2. The new parser checks this header before reporting accepted sign-in. Remaining character data and persistent world connection are not yet implemented.


Native sign-in acceptance was confirmed by the user on October 6. Character-list handler 0x5a17ac receives the remainder after the first account-header FF. It reads a one-byte count, skips the count segment, then consumes four FF-delimited segments per character (name, title, guild, stats), capped at three. Stats must contain at least 26 bytes; first four decode to character ID. Names are displayed without the official initial-letter capitalization helper. The native client validates this layout and keeps a recognized authenticated connection open for up to five minutes, answering synchronization/keepalive and allowing explicit disconnect. Character selection/world-entry packets are not yet sent. Live roster verification remains pending; fixtures cover parsing and post-login keepalive.

Live 82-byte accepted reply failed initial roster parsing. Reinspection of 0x5a1859 and 0x5a18ea shows the count is taken from the first byte, with the rest of that delimiter segment skipped; its length is not required to equal one. Reader 0x4f8ca8 also returns an unterminated final field at end of input. Native parser now follows both behaviors. On remaining mismatches it reports only field lengths and fixed parser errors, not field contents. Live verification pending.

The next live failure reported “Unsupported character count” with FF field lengths 13,2,11,8,9,31,0 (82-byte body). Count value itself was not retained. Official loop 0x5a235f checks index < decoded count AND index < 3 rather than rejecting counts above three; missing records are skipped when stats length is below 26. Native parser now caps the loop at three and stops at EOF. A synthetic fixture matches the observed field lengths with a deliberately large count; this is structural regression evidence, not a capture of the user's data.
